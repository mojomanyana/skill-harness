# Your skill scored an A. The model would have passed anyway.

Here's the most expensive mistake you can make when writing an agent skill: you
write a `SKILL.md`, you run your scenarios, you get an A, and you conclude the
skill works.

You have not measured the skill. You measured the model plus the skill, and
those are very different things. A capable model passes a lot of scenarios with
no skill at all — good judgment about when to simplify code, or a refusal to
add a speculative plugin, is behavior plenty of models already have. If it would
have passed anyway, your `SKILL.md` contributed nothing, and the A told you the
opposite.

The only way to know is to run the scenarios with the skill switched off and
compare. `skill-harness` now does that for you, and calls the difference **lift**:

```
  GRADE: B (80%) — 4/5 — NOT READY
  LIFT:  +2 net (3 gained, 1 regressed) · 1 inconclusive
```

Four numbers, each one an answer to a question the grade can't address:

- **gained** — failed without the skill, passes with it. This is your skill working. It is the only number that justifies the file existing.
- **regressed** — passed without the skill, fails with it. Your skill made the model *worse* at something. This happens more than people expect, usually when a skill over-constrains a model that was already fine.
- **kept** — passed either way. Not a failure, but not evidence for your skill either. A scenario stuck permanently in `kept` is a scenario that isn't testing your skill.
- **inconclusive** — see below.

## The number that makes the other three trustworthy

`inconclusive` is the one I'd argue about if someone told me to drop it.

When a run errors — a harness timeout, an empty reply — the obvious thing is to
treat it as a fail. That's what scoring does, and for scoring it's right: you
didn't pass.

But lift isn't scoring. Lift is a *comparison*, and in a comparison a red-side
ERROR is not evidence that the skill-less agent couldn't do the task. It's the
absence of evidence. Count it as a fail and every `red ERROR → green PASS` becomes
a "gain", so your lift number quietly starts measuring how flaky your
infrastructure is while looking exactly like skill value. The same goes for an
unresolved judge misfire: a verdict the judge contradicted itself on is not a
fact about the agent.

So they're excluded, counted separately, and shown. A lift of `+1 · 4 inconclusive`
is telling you to fix your harness before you believe anything.

## Two design decisions worth stealing

**Lift is never stored.** It's derived from whatever runs are on disk every time
you ask. A lift is a fact about a *pair* of runs, so caching it inside one run's
`results.yaml` would go stale the moment a new baseline landed — and a stale
number that looks current is worse than no number. The bonus: it works
retroactively. If you ran a red baseline weeks ago, lift appears for it today,
with no re-runs and no tokens spent.

**"Not measured" is not "no effect".** If there's no red run, the report says
`no red baseline` and offers the command. It does not show a zero. A zero is a
finding; silence is a missing experiment. Conflating them is how dashboards start
lying to you.

## Try it

```bash
skill-harness run <skill> --skills <root> --mode red     # baseline, skill off
skill-harness run <skill> --skills <root> --mode green   # skill active
skill-harness review <skill> --skills <root>             # ↑/↓ markers per scenario
```

If you write skills, run this against one you're proud of. I'd genuinely like to
hear how many of your scenarios come back `kept` — my guess is more than you
expect, and the ones that do are showing you exactly which parts of your
`SKILL.md` are load-bearing and which are decoration.
