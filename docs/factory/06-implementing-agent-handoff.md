## 3. Rules you must carry across sessions

- **Observation stays external.** Read available files, streams and ledgers. No monitoring prompts, hidden messages, session-entry writes or observer-driven steering. Coverage gaps stay visible; optional observation cannot delay the worker. Required control logging retains its failure rules.
- **Control stays deterministic.** Models propose and advise. No model call decides dispatch, grants or a live control gate. Calibrated evidence gains only the scope explicitly authorized by policy; trust never grants itself authority.
- **Separate roles and evidence.** Preserve canonical proposer/subject/judge identities and fresh contexts. A new chat or alias of the same model does not provide the required separation. Independent contexts alone are not proof of model independence. Keep objective checks, model judgments, human decisions and observed outcomes distinguishable.
- **Respect measurement validity.** Missing/untrusted delivery stays `ERROR`; known incorrect delivery stays `NOT-MEASURED`. Skip judging as required. Preserve fixed-model comparison invariants. Never turn an unsupported extension-bearing experiment green by removing its measurement gate.
- **Use the packet's assurance minimum.** Read Principal's effective profile and shipped event contract. Critical work requires its real isolation, critique, reviews and fresh tree-bound evidence. Missing controls return `BLOCKED_CRITICAL_ASSURANCE`; do not downgrade to make progress appear complete.
- **Reuse concrete authorization.** A recorded design approval or experiment charter covers work within its stated bounds. Do not ask again merely because a new packet/session starts. For a genuinely missing consequential decision, finish the design, validation, rollback and abort proposal first; identify the exact rule requiring the decision and ask one focused question. Never label an unseen design approved.
- **Keep active inputs pinned.** Record intent, source, artifact, configuration, grant and evaluation identities. Supersede affected acceptance when those inputs change. Historical evidence remains intact and its current applicability is a separate projection.
- **Finish on the branch.** The packet briefs choose that finish mode. No merge, push, release, production action or broad cleanup is implied. Preserve user changes, owned evidence and historical records. Preferred cleanup is a bounded removal hypothesis with surviving obligations, not a file-count target.

An implementation kickoff authorizes the work it states; generating this handoff itself does not execute those packets. Benchmark subject/judge calls require the concrete authorized experiment configuration. Subscription calls still consume resources. `regate` and capture promotion can spend tokens; do not count them as universally offline.

## 4. Procedure for each packet

1. **Select eligible work.** Read the full packet in the guide, its dependencies and current report. Pick the earliest useful ready packet in the guide's waves. Record any reason for working out of order. A dependent route must have its own evidence; an unrelated pass is insufficient.

2. **Reconcile the starting state.** Identify actual repo/worktree/branch, dirty state, dependency commits and trees, loaded artifacts, existing tasks/processes and approvals. Preserve unrelated changes. Do not replay a launch or mutation with ambiguous completion merely because its last message is missing.

3. **Bind ownership and authority.** Assign one writer and an integration owner; create/reuse an owned isolated workspace as required. Read the guide before restricting Build. Record packet ID, scope, assurance, finish intent, dependency identities, relevant approvals and the exact requirement text through the existing workflow.

4. **Plan a verifiable slice.** Inspect every named source seam. Resolve actual commands/UI actions and expected outputs for the guide's Done conditions. Identify compatibility and negative controls. Reuse existing commands, schemas and fixtures; do not add a redundant framework. For critical scope, perform the required fresh plan critique before issuing immutable task packets or starting Build.

5. **Resolve consequential decisions once.** Where required, present the concrete design with validation, observability, rollback, abort and one-way effects. Cite already-covered approval when applicable. A remaining question blocks only the affected work; continue unrelated authorized read-only preparation or independent ready packets.

6. **Build under the real gates.** Keep one source writer and the declared writer root. Use Principal's native event/packet contract rather than invented payloads. Edit generator sources and regenerate where applicable. Keep optional cleanup out of a functional packet unless it is necessary to that packet's behavior.

7. **Verify and review the actual candidate.** Run meaningful targeted checks, required adverse cases and the applicable final suite after the last change. Bind receipts to the real candidate tree, including uncommitted output. Use fresh reviews and adjudicate findings before repair. Respect Principal's repair-round limit; do not quietly restart it in a new session.

8. **Return a completion or BLOCKED report.** Use section 7. Provide exact commands/actions, expected versus actual results, evidence paths and supported scope. The worker returns this to the integration owner; it does not write another repo's report. Keep the source branch and record its exact commit/tree or explicitly uncommitted candidate identity.

9. **Integrate evidence, then continue.** The integration owner checks dependency pins, reviews, tree freshness and all Done conditions, then updates the tracker and report. Dependency consumers may use an explicitly pinned completed branch/worktree without merging it to main. Use immutable dependency source artifacts; do not read an actively changing writer tree as a completed input. A composition that needs merging must have a named owner and the required authorization.

10. **Checkpoint before yielding.** Record the next exact action, current processes/effects, unresolved decisions and evidence locations. Continue authorized ready work autonomously. Do not stop after a plan or a green unit test when required implementation/review work remains.

Record the verified product tree separately from later report-only commits. Updating the report must not create a self-referential requirement to hash the report containing its own hash. Any actual product/dependency mutation after verification requires fresh evidence for the changed scope.

## 6. Resume protocol

On any new session, context reset, interruption or owner handoff:

1. Read this handoff, the relevant build-guide packet and the latest campaign report/checkpoint. Recover the actual owner workspace from the recorded resume prompt. If unavailable, inspect registered skill-harness worktrees and their `docs/factory/BUILD-REPORT.md` files, matching campaign identity, owner and document identities. Do not select by modification time alone or initialize a second tracker because the canonical checkout lacks one. Resolve competing ownership before writes.
2. Inspect current repo/worktree/branch and dirty state, source/tree identities, installed artifacts, live processes, leases and existing assurance records. Treat a previous chat summary as a pointer to evidence, not proof of completion.
3. Reconcile the last operation. Determine whether a launch, write, evaluation or external effect finished, is still active, failed or remains ambiguous. Check retained receipts and actual state. Do not rerun, kill, delete or take ownership of an unidentified process/worktree.
4. Revalidate dependency and candidate identity against receipts. If they changed, invalidate only affected verification/acceptance, retain history and replan under the existing contract. Do not reset, stash or overwrite unrelated changes to make the tree look clean.
5. Recover current approvals, spend already incurred, remaining allowance, effective assurance and repair count. Reuse covered approvals. Missing credentials, role identity or critical controls remain explicit blockers; do not silently substitute a different model or weaker profile.
6. Resume the existing valid run/task where supported. If it cannot be resumed, record why, preserve/supersede the old task through the real contract and link the replacement run. A new session does not reset budgets, repair limits or effect history.
7. Record one concrete next action, then execute it if authorized. If blocked, return the format below and continue any independent ready work. The absence of the future archive/dispatcher is not a reason to invent its API during bootstrap.
